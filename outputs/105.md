> **Tarih:** 2026-03-02
> **Kapsam:** TradeHub B2B2B Marketplace — 7 app, 89 JSON-veri taşıyan alan
> **Referans:** `tr_tradehub/JSON_FIELD_AUDIT.md` (baseline), Listing DocType (migrated pattern)
> **Post-apply:** `bench migrate && bench clear-cache`

## Özet

Bu doküman, TradeHub platformundaki tüm DocType JSON dosyalarını tarayarak JSON verisi taşıyan alanları analiz eder ve uygun Frappe field tiplerine dönüşüm planı sunar. **Hiçbir kod değişikliği yapılmaz** — yalnızca analiz ve planlama çıktısıdır.

### Taranan Alan Tipleri

| Fieldtype | Bulunan | Dönüştürülecek | JSON Kalacak | Kod Kalacak | Migre Edilmiş |
|-----------|---------|----------------|--------------|-------------|---------------|
| JSON | 50 | 25 | 19 | — | 6 |
| Code (options=JSON) | 23 | 1 | 5 | 17 | — |
| Code (CSS/HTML/Python/JS) | 12 | 0 | 0 | 12 | — |
| Text/Small Text (JSON veri) | 4 | 2 | 1 | — | — |
| **TOPLAM** | **89** | **28** | **25** | **29** | **6** |

> **Not:** 1 Code(JSON) alanı (PIM Product.amazon_bullet_points) dönüşüm adayıdır — basit string dizisi olduğu için Child Table'a alınabilir.

### Karar Ağacı (Decision Tree)

```
Alan JSON verisi taşıyor mu?
├─ Object dizisi (array of objects) → Table (yeni Child DocType)
├─ Basit referans dizisi (DocType name'leri) → Table MultiSelect
├─ Tek referans → Link
├─ Sabit enum → Select
├─ Boolean → Check
├─ API response / hesaplama geçmişi / audit snapshot → JSON KALSIN
├─ UI konfigürasyonu / mapping → JSON KALSIN
├─ Şablon kodu (Jinja/Python/CSS/HTML) → Code KALSIN
└─ Zaten migrate edilmiş (hidden + read_only) → ALREADY MIGRATED
```

### 3.6 Commission Rule — day_of_week_restrictions Özel Dönüşümü

Mevcut `day_of_week_restrictions` JSON alanı `[1,2,3,4,5]` formatında günleri saklar. Önerilen dönüşüm:

```
Mevcut: day_of_week_restrictions (JSON) → [1, 2, 3, 4, 5]

Yeni (7 Check field):
  monday    (Check, default=0)
  tuesday   (Check, default=0)
  wednesday (Check, default=0)
  thursday  (Check, default=0)
  friday    (Check, default=0)
  saturday  (Check, default=0)
  sunday    (Check, default=0)
```

**Gerekçe:** Haftanın günleri sabit bir küme (7 eleman), dinamik değil. 7 adet Check field daha açık, sorgulanabilir ve form'da görsel olarak daha net.

**Alternatif:** `Select` fieldtype ile `\n` ile ayrılmış günler ve MultiSelect widget kullanımı.

#### Teknik Bağımlılıklar
| Bağımlılık | Açıklama |
|------------|----------|
| Mevcut Python API'leri | JSON parse eden tüm Python fonksiyonları güncellenmeli |
| Client-side JS | JSON field'a yazan tüm JS kodları Table widget'a çevrilmeli |
| REST API tüketicileri | Harici sistemler JSON formatında veri bekliyorsa backward compatibility sağlanmalı |
| Rapor sorguları | JSON field'a `json_extract()` ile sorgulayan raporlar güncellenmeli |

### 5.2 Riskler

| Risk | Seviye | Açıklama | Mitigasyon |
|------|--------|----------|------------|
| **Veri kaybı** | Yüksek | Migration sırasında JSON verisi düzgün parse edilemezse veri kaybı | Migration öncesi backup, JSON field'ları silmeden önce geçiş dönemi |
| **Malformed JSON** | Orta | Bazı JSON alanlarında bozuk veri olabilir | Migration patch'te try/except ile hata yönetimi, hatalı kayıtları loglama |
| **Performans** | Düşük | Child table'lar ek JOIN sorgusu gerektirir | Frappe'nin yerleşik child table optimizasyonları yeterli |
| **API uyumluluğu** | Orta | Harici entegrasyonlar JSON formatında veri bekliyorsa kırılabilir | Geçici olarak hem JSON hem child table verisi tutma, API'de backward compatibility layer |
| **Commission Rule karmaşıklığı** | Orta | 6 JSON alanı → 3 child table + 7 check field → karmaşık migration | Aşamalı migration: önce seller/category, sonra day_of_week, son olarak override_by |
| **Payment Intent kritik veri** | Yüksek | Ödeme verileri hassas, migration hatası finansal etki yaratabilir | Staging'de kapsamlı test, production'da read-only geçiş dönemi |
| **Moderation history bütünlüğü** | Orta | read_only audit log verisi — migration'da sıralama korunmalı | idx field ile sıralama, original JSON backup |

### 5.3 Migration Stratejisi

```
Adım 1: Child DocType'ları oluştur (bench migrate)
        ↓
Adım 2: Parent DocType'lara yeni Table field'ları ekle (JSON field'ları TUTARAK)
        ↓
Adım 3: Migration patch çalıştır (JSON → child table veri kopyalama)
        ↓
Adım 4: Python/JS kodlarını güncelle (child table API'si kullanımı)
        ↓
Adım 5: JSON field'ları hidden + read_only yap
        ↓
Adım 6: Doğrulama dönemi (2-4 hafta)
        ↓
Adım 7: JSON field'ları tamamen kaldır
```

### 5.4 Migration Patch Örnek Yapısı

```python
# patches/v1_x/convert_json_to_child_tables.py
import frappe
import json

def execute():
    """Convert JSON fields to child tables."""

    # Example: Payment Intent installment_plan
    for pi in frappe.get_all("Payment Intent",
        filters={"installment_plan": ["is", "set"]},
        fields=["name", "installment_plan"],
        limit_page_length=0
    ):
        try:
            data = json.loads(pi.installment_plan) if isinstance(pi.installment_plan, str) else pi.installment_plan
            if not isinstance(data, list):
                continue

            doc = frappe.get_doc("Payment Intent", pi.name)
            for idx, item in enumerate(data, 1):
                doc.append("installments", {
                    "installment_number": item.get("installment_number", idx),
                    "due_date": item.get("due_date"),
                    "amount": item.get("amount", 0),
                    "status": item.get("status", "Pending"),
                })
            doc.flags.ignore_validate = True
            doc.flags.ignore_permissions = True
            doc.save()
        except Exception as e:
            frappe.log_error(
                f"JSON migration failed for Payment Intent {pi.name}: {str(e)}",
                "JSON to Child Table Migration"
            )

    frappe.db.commit()
```
