## Ozet

Bu dokuman, TradeHub B2B2B marketplace platformundaki tum DocType'lardaki `fetch_from` alanlarinin kapsamli analizini icerir. Mevcut 309 fetch_from alani dogrulanmis, 8 adet read_only:1 eksikligi tespit edilmis, 2 adet bos fetch_from ifadesi bulunmus ve ~120 yeni fetch_from alani onerilmistir. Ayrica JS tarafinda clear-on-change mantigi planlanmistir.

### 3.4 Referans Pattern'ler (Mevcut En iyi Uygulamalar)

Asagidaki DocType'lar fetch_from pattern'i icin referans olarak kullanilmistir:

| DocType | fetch_from Sayisi | Pattern Ozeti |
|---------|-------------------|---------------|
| **Payment Plan** | 17 | Tek Link (order) -> tum buyer/seller/tenant transitif olarak alinir |
| **Shipment** | 20 | Coklu Link (order, sub_order, carrier) -> her kaynaktan ilgili alanlar |
| **Buy Box Entry** | 16 | Iki bagimsiz Link (sku_product, seller) -> urun ve satici bilgileri ayri ayri |
| **Subscription** | 18 | Coklu Link + iki-adim zincir (seller_profile.tenant -> tenant.tenant_name) |

**Ortak Pattern Kurallari:**
1. Her fetch_from alani `read_only: 1` olmalidir (kasitli override'lar haric)
2. Tenant alani her zaman `seller.tenant` veya `buyer.tenant` uzerinden otomatik gelmeli
3. tenant_name alani her zaman `tenant.tenant_name` uzerinden fetch edilmeli
4. Link tipi fetch_from alanlari (orn: `buyer`, `seller`, `tenant`) hem Link hem fetch_from olarak tanimlanir
5. Iki-adim zincir (orn: `seller_profile.tenant` -> `tenant.tenant_name`) Frappe'nin destekledigi gecerli bir yontemdir

### 4.3 JS Dosyalari — Clear-on-Change Mantigi (~30 dosya)

Asagidaki DocType'larda birden fazla bagimsiz Link alani vardir ve kullanici bir Link alanini degistirdiginde/temizlediginde, o Link'ten fetch edilen tum bagli alanlar da temizlenmelidir. Bu mantik JS dosyasinda implement edilir.

> **Not**: Halihazirda referans pattern'lerde (Payment Plan, Buy Box Entry, Shipment, Subscription) JS dosyasi **bulunmamaktadir**. Frappe, fetch_from alanlarini Link degistiginde otomatik olarak gunceller. Ancak Link alani **temizlendiginde** (set to empty), fetch_from alanlari otomatik olarak temizlenmez — bu durum icin JS gereklidir.

**JS Dosyasi Gereken DocType'lar ve Pattern:**

```javascript
// Ornek: Listing DocType icin clear-on-change mantigi
// Dosya: listing.js
frappe.ui.form.on('Listing', {
  seller: function(frm) {
    if (!frm.doc.seller) {
      // seller temizlendiginde bagli alanlari temizle
      frm.set_value('seller_name', '');
      frm.set_value('seller_company', '');
      frm.set_value('tenant', '');
      frm.set_value('tenant_name', '');
    }
  },
  category: function(frm) {
    if (!frm.doc.category) {
      frm.set_value('category_name', '');
    }
  }
});
```

frappe.ui.form.on('Listing', {
  // === Task 104: Dynamic Filters ===
  setup: function(frm) {
    frm.set_query('subcategory', function() {
      return { filters: { parent_category: frm.doc.category } };
    });
  },

  // === Task 115: Clear-on-Change ===
  seller: function(frm) {
    if (!frm.doc.seller) {

      frm.set_value('seller_company', '');

### 5.3 Riskler

| Risk | Olasilik | Etki | Azaltma |
|------|----------|------|---------|
| Mevcut veri tutarsizligi | Orta | Eski kayitlarda yeni fetch_from alanlari bos kalir | `fetch_if_empty: 1` varsayilan olarak Frappe sadece bos alanlari doldurur; migration patch ile bulk update yapilanilabilir |
| Performance etkisi | Dusuk | 120 yeni fetch_from alani DB sorgularini artirabilir | Frappe fetch_from tek bir SELECT ile calisir, performans etkisi minimal |
| JS dosyasi catismasi | Orta | Task 104 ve 115 ayni JS dosyalarini hedefliyor | Tek JS dosyasinda birlestirilmeli, ayri fonksiyonlar icinde organize edilmeli |
| Field siralama sorunu | Dusuk | Yeni alanlar eklenmesi mevcut form layout'unu bozabilir | field_order listesinde dogru yere eklenmeli, Tab Break plani (101) ile uyumlu olmali |
| Upstream DocType degisiklikleri | Dusuk | Kaynak DocType'ta alan adi degisirse fetch_from kirilir | Ayni ekibin kontrol ettigi DocType'lar kullaniliyor, dis bagimlilik yok |
| Seller Profile tenant fetch_from cakismasi | Orta | Seller Profile'da tenant hem `reqd: Yes` hem `fetch_from: organization.tenant` — organization bos ise tenant elle girilmeli | Seller Profile.tenant icin `fetch_if_empty: 1` kullaninilmali, read_only olmamali |

### 5.4 Ozel Durumlar

1. **Subscription.current_price ve grace_period_days**: Bu 2 alan kasitli olarak `read_only` yapilmamistir. Kullanici, varsayilan degeri override edebilir. Bu "fetch_if_empty + editable" pattern'idir.

2. **Buy Box Entry.seller_response_rate ve seller_buy_box_win_rate**: Bu 2 alanin `fetch_from` degeri bos string (`""`). Kaynak DocType'ta (Seller Profile) bu alanlar mevcut degildir. Ya alanlar kaldirilmali ya da Seller Profile'a ilgili alanlar eklenmeli.

3. **Iki-adim zincir fetch_from**: Subscription DocType'ta `seller_profile.tenant` -> `tenant.tenant_name` seklinde iki asamali fetch_from kullanilmaktadir. Bu, Frappe'nin destekledigi gecerli bir yontemdir ve diger DocType'larda da uygulanabilir.

4. **Seller Profile.tenant**: Bu alan hem `reqd: Yes` (Organization olmadan da tenant secilmeli) hem de `fetch_from: organization.tenant` olarak tanimli. Organization secildiginde tenant otomatik gelir, secilmediginde kullanici elle girer. Bu nedenle `read_only: 1` **eklenmemeli** ancak `fetch_if_empty: 1` eklenmeli.
