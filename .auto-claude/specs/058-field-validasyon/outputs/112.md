# 112 -- Role-Based Field Authorization Plan

## 1. Executive Summary

This document defines the comprehensive field-level authorization strategy for the TradeHub B2B Marketplace platform. It categorizes **every field** across **all 124 parent DocTypes** in **7 Frappe apps** into one of three authorization tiers:

| Category | Label | Count (approx.) | Description |
|----------|-------|-----------------|-------------|
| **(a)** | SYSTEM-GENERATED / LOCKED | ~1,050 | Auto-IDs, timestamps, computed totals, fetch_from fields, naming_series, audit trails |
| **(b)** | ADMIN-EDITABLE | ~2,460 | System config, moderation decisions, status overrides, tenant assignments, pricing rules, compliance decisions |
| **(c)** | USER-EDITABLE | ~1,465 | Content fields, quantity inputs, selections, attachments, descriptions, comments |

**Total fields scanned:** ~4,975 across 124 parent DocTypes (excluding Section Break, Column Break, Tab Break, and Table child-link fields).

### Apps Covered

| # | App | Parent DocTypes | Total Fields | Key Domain |
|---|-----|----------------|-------------|------------|
| 1 | tradehub_commerce | 22 | ~1,056 | Orders, payments, carts, quotations, RFQs, commissions |
| 2 | tradehub_seller | 19 | ~971 | Seller profiles, listings, SKUs, KPIs, scores, tiers |
| 3 | tradehub_catalog | 24 | ~774 | Products, PIM, attributes, categories, brands, media |
| 4 | tradehub_core | 20 | ~621 | Buyers, tenants, organizations, ECA rules, geography |
| 5 | tradehub_compliance | 23 | ~610 | Certificates, consent, contracts, messaging, moderation, reviews |
| 6 | tradehub_logistics | 7 | ~610 | Shipments, carriers, tracking, shipping rules, lead times |
| 7 | tradehub_marketing | 9 | ~335 | Campaigns, coupons, group buys, storefronts, subscriptions |

### Key Principles

1. **Frappe-native first** -- Use `read_only`, `set_only_once`, `permlevel`, `hidden`, `depends_on`, and `fetch_from` before resorting to custom JS.
2. **Server-side is authoritative** -- `set_df_property()` in JS is a UX enhancement; Python `validate()` is the enforcement layer.
3. **Defense in depth** -- System-generated fields must be protected at both JSON schema level (`read_only:1`) AND Python validation (`if self.has_value_changed("field"): frappe.throw()`).
4. **Multi-tenant isolation** -- Tenant fields are auto-populated and locked. No user (including admin) should manually set tenant fields.
5. **Role-based granularity** -- Buyer and Seller roles see different field editability on shared DocTypes (e.g., Order).

## 2. Field Categories Definition

### Category (a): SYSTEM-GENERATED / LOCKED

Fields that are **never directly edited by any human user**. They are populated by code, computed from other fields, or auto-filled from linked records.

**Identification rules:**
- `read_only: 1` + `fetch_from: <source>` = auto-populated from linked record
- `read_only: 1` + computed field (e.g., `days_until_expiry`, `total_amount`, `balance_amount`)
- Hidden `naming_series` with `hidden: 1`
- Audit timestamps: `created_at`, `verified_at`, `signed_at`, `delivered_at`, etc.
- System counters: `certificate_count`, `total_sales_count`, `shipment_count`, etc.
- Auto-generated identifiers: `shipment_id`, `sync_id`, `external_id`, `offer_code`
- Tenant name fields: `tenant_name` (always `read_only:1` + `fetch_from:tenant.tenant_name`)
- Link fields set by system workflow: `renewed_from`, `renewed_to`, `amended_from`

**Protection mechanism:** `read_only: 1` in JSON + Python `validate()` guard.

### Category (b): ADMIN-EDITABLE

Fields that **only System Manager, Tenant Admin, or equivalent admin roles** can modify. Regular Buyer/Seller users cannot edit these.

**Identification rules:**
- DocTypes with only admin-level permissions (System Manager, Administrator, Tenant Admin)
- `status` fields on lifecycle-managed DocTypes (admin/system transitions)
- Toggle fields: `enabled`, `is_active`, `is_default`, `is_global`, `is_verified`, `is_approved`, `is_restricted`
- Verification fields: `verification_status`, `verification_notes`, `verified_by`
- Admin notes: `internal_notes`, `admin_notes`, `rejection_reason`, `moderation_notes`
- Financial config: `commission_rate`, `commission_percentage`, `platform_fee`
- Credential fields: `api_key`, `api_secret`, `api_password`, `webhook_secret` (Password type)
- Tenant assignment: `tenant` (Link to Tenant, non-read_only)

**Protection mechanism:** `permlevel: 1` in JSON (requires "Permlevel 1" role permission) + custom JS `set_df_property("fieldname", "read_only", 1)` for non-admin roles.

### Category (c): USER-EDITABLE

Fields that **end-users (Buyer, Seller, or any logged-in user)** can create/modify within their authorized scope.

**Identification rules:**
- DocTypes where Buyer/Seller/All roles have `create` or `write` permission
- Content fields: names, descriptions, titles, notes
- Quantity/pricing inputs: `quantity`, `unit_price`, `min_order_amount`
- Selection fields: `order_type`, `payment_terms`, `incoterm`
- Upload fields: `certificate_document`, `signed_pdf`, `logo`
- Link selections: `buyer`, `seller`, `certificate_type`, `category`
- Date inputs: `issue_date`, `expiry_date`, `start_date`, `end_date`
- Address fields: `address_line_1`, `city`, `state`, `country`, `postal_code`

**Protection mechanism:** Standard `permlevel: 0` (default) with role-based DocType permissions controlling access.

## 3. Frappe Permission Mechanisms Overview

### 3.1 DocType-Level Permissions

Frappe permissions are defined per-DocType per-Role with granularity:

| Permission | Description | Usage |
|-----------|-------------|-------|
| `read` | View the document | All relevant roles |
| `write` | Edit existing documents | Roles that can modify |
| `create` | Create new documents | Roles that can initiate |
| `delete` | Delete documents | Usually System Manager only |
| `submit` | Submit workflow documents | Not used in TradeHub (no submittable DocTypes found) |
| `cancel` | Cancel submitted documents | Not used in TradeHub |
| `amend` | Amend cancelled documents | Not used in TradeHub |
| `report` | View reports | Usually all reading roles |
| `export` | Export data | Usually all reading roles |
| `print` | Print document | Usually all reading roles |
| `email` | Email document | Usually all reading roles |
| `share` | Share with other users | Usually admin + owners |
| `if_owner` | Permission applies only to documents owned by the user | Key for Buyer/Seller isolation |

### 3.2 Field-Level Permission (permlevel)

Frappe supports **10 permission levels** (0-9) on individual fields:

```
permlevel: 0  -- Default. Controlled by standard DocType permissions.
permlevel: 1  -- Requires explicit "Permlevel 1" grant in role permissions.
permlevel: 2  -- Requires explicit "Permlevel 2" grant.
...
permlevel: 9  -- Highest restriction level.
```

**TradeHub Strategy:**
- `permlevel: 0` -- User-editable fields (category c)
- `permlevel: 1` -- Admin-editable fields (category b)
- System-generated fields use `read_only: 1` instead of permlevel (they should never be editable at any level)

### 3.3 Field-Level Properties

| Property | JSON Key | Effect |
|----------|----------|--------|
| Read Only | `read_only: 1` | Field visible but not editable by anyone in the UI |
| Set Only Once | `set_only_once: 1` | Editable only on new documents, locked after first save |
| Hidden | `hidden: 1` | Field not visible in UI (still accessible via API) |
| Fetch From | `fetch_from: "link_field.source_field"` | Auto-populated when link field changes |
| Mandatory | `reqd: 1` | Must have a value before save |
| Mandatory Depends On | `mandatory_depends_on: "eval:..."` | Conditionally mandatory |
| Read Only Depends On | `read_only_depends_on: "eval:..."` | Conditionally read-only |
| Depends On | `depends_on: "eval:..."` | Conditionally visible |
| Allow on Submit | `allow_on_submit: 1` | Editable even after submission |

### 3.4 Custom JS set_df_property()

For dynamic field authorization based on the current user's role:

```javascript
frappe.ui.form.on("Order", {
    refresh(frm) {
        // Make admin-only fields read-only for non-admin users
        if (!frappe.user_roles.includes("System Manager")) {
            frm.set_df_property("commission_rate", "read_only", 1);
            frm.set_df_property("internal_notes", "hidden", 1);
        }
    }
});
```

### 3.5 Python Server-Side Enforcement

```python
class Order(Document):
    def validate(self):
        self._protect_system_fields()
        self._protect_admin_fields()

    def _protect_system_fields(self):
        """Prevent modification of system-generated fields."""
        system_fields = ["subtotal", "tax_amount", "total_amount", "balance_amount"]
        for field in system_fields:
            if self.has_value_changed(field) and not self.is_new():
                frappe.throw(
                    _("Field {0} is system-generated and cannot be modified directly.").format(field),
                    frappe.PermissionError
                )

    def _protect_admin_fields(self):
        """Prevent non-admin users from modifying admin-only fields."""
        if "System Manager" not in frappe.get_roles():
            admin_fields = ["commission_rate", "internal_notes"]
            for field in admin_fields:
                if self.has_value_changed(field):
                    frappe.throw(
                        _("You do not have permission to modify {0}.").format(field),
                        frappe.PermissionError
                    )
```

## 7. Implementation Plan

### 7.1 Phase 1: JSON Schema Hardening (read_only enforcement)

**Goal:** Ensure all category (a) fields have `read_only: 1` in their DocType JSON.

**Action:** Audit each DocType JSON and add `read_only: 1` to any category (a) field that currently lacks it.

```
For each DocType JSON:
  For each field in category (a):
    IF field.read_only != 1:
      SET field.read_only = 1
      LOG: "{doctype}.{fieldname} -- added read_only:1"
```

**Estimated changes:** ~50 fields across all apps that are system-generated but missing `read_only: 1` (primarily in DocTypes created programmatically like Tracking Event, Consent Audit Log where fields are not marked read_only but the DocType itself is only created by code).

### 7.2 Phase 2: permlevel Assignment for Admin Fields

**Goal:** Set `permlevel: 1` on all category (b) fields in DocTypes where users (Buyer/Seller/All) have write access.

**Target DocTypes:** Only those with mixed permissions (both admin AND user roles with write access):
- Order, Sub Order, Marketplace Order, Cart, Quotation, Payment Plan, Incoterm Price
- Seller Profile, Listing, SKU Product, Seller Store, Buy Box Entry, Seller Application
- Certificate, Consent Record, Message, Review, Sample Request

- Campaign, Coupon, Group Buy, Group Buy Commitment, Storefront, Subscription, Wholesale Offer
- Brand, Product Category, Product Variant, Product Attribute, SEO Meta

### 7.3 Phase 3: Custom JS for Dynamic Authorization

**Goal:** Add client-side UX enforcement via `set_df_property()` for complex authorization rules that cannot be expressed through permlevel alone.

**Pattern:**

```javascript
// Standard authorization pattern for all TradeHub DocTypes
frappe.ui.form.on("DocType Name", {
    refresh(frm) {
        tradehub.apply_field_authorization(frm);
    }
});

// Centralized authorization utility
tradehub.apply_field_authorization = function(frm) {
    const is_admin = frappe.user_roles.includes("System Manager") ||
                     frappe.user_roles.includes("Tenant Admin");
    const is_seller = frappe.user_roles.includes("Seller") ||
                      frappe.user_roles.includes("Satici") ||
                      frappe.user_roles.includes("Satici Admin");
    const is_buyer = frappe.user_roles.includes("Buyer") ||
                     frappe.user_roles.includes("Alici Admin") ||
                     frappe.user_roles.includes("Alici Editor");

    // Hide admin-only sections for non-admin users
    if (!is_admin) {
        frm.set_df_property("internal_notes", "hidden", 1);
        frm.set_df_property("admin_notes", "hidden", 1);
    }

    // Role-specific field visibility
    if (is_buyer && !is_admin) {
        // Buyer cannot see seller-internal fields
        frm.set_df_property("seller_notes", "hidden", 1);
        frm.set_df_property("commission_rate", "hidden", 1);
    }

    if (is_seller && !is_admin) {
        // Seller cannot modify buyer-owned fields
        frm.set_df_property("buyer_notes", "read_only", 1);
    }
};
```

**Key scenarios requiring custom JS:**
1. **Order:** Buyer sees buyer_notes (editable) + seller_notes (hidden). Seller sees seller_notes (editable) + buyer_notes (read-only).
2. **Listing:** Seller sees all content fields (editable). Admin sees moderation fields (editable). Buyer sees everything (read-only).
3. **Seller Profile:** Seller sees contact/banking fields (editable). Admin sees verification/tier/restriction fields (editable).
4. **Review:** Buyer sees rating/content fields (editable). Admin sees moderation fields (editable). Seller sees everything (read-only).

### 7.4 Phase 4: Python Server-Side Validation

**Goal:** Add `validate()` guards as the authoritative enforcement layer.

**Pattern for each DocType:**

```python
class Order(Document):
    # System fields that must never be manually changed
    SYSTEM_FIELDS = [
        "subtotal", "tax_amount", "total_amount", "discount_amount",
        "balance_amount", "paid_amount", "advance_amount",
        "buyer_name", "seller_name", "tenant", "tenant_name",
        "order_number", "tracking_number",
        "confirmed_date", "processing_start_date", "shipped_date",
        "delivered_date", "completed_date", "cancelled_at",
        "linked_sales_order", "linked_purchase_order",
        "linked_invoice", "linked_delivery_note"
    ]

    # Admin-only fields that require System Manager role
    ADMIN_FIELDS = [
        "status", "payment_status", "tax_rate", "commission_rate",
        "internal_notes", "auto_cancel", "cancel_deadline"
    ]

    def validate(self):
        if not self.is_new():
            self._protect_system_fields()
            self._protect_admin_fields()

    def _protect_system_fields(self):
        for field in self.SYSTEM_FIELDS:
            if self.has_value_changed(field):
                # Allow changes from whitelisted methods only
                if not getattr(self, "_allow_system_field_update", False):
                    frappe.throw(
                        _("{0} is a system-generated field").format(field),
                        frappe.ValidationError
                    )

    def _protect_admin_fields(self):
        if "System Manager" not in frappe.get_roles():
            for field in self.ADMIN_FIELDS:
                if self.has_value_changed(field):
                    frappe.throw(
                        _("Only administrators can modify {0}").format(field),
                        frappe.PermissionError
                    )

    def calculate_totals(self):
        """System method that is allowed to update system fields."""
        self._allow_system_field_update = True
        try:
            self.subtotal = flt(sum(flt(item.amount) for item in self.items))
            self.discount_amount = flt(self.subtotal * flt(self.discount_percentage) / 100)
            self.tax_amount = flt((self.subtotal - self.discount_amount) * flt(self.tax_rate) / 100)
            self.total_amount = flt(self.subtotal - self.discount_amount + self.tax_amount + flt(self.shipping_cost))
            self.balance_amount = flt(self.total_amount - flt(self.paid_amount))
        finally:
            self._allow_system_field_update = False
```

## 8. Multi-Tenant Awareness

### 8.1 Tenant Field Patterns

All TradeHub DocTypes follow one of three tenant isolation patterns:

| Pattern | Description | Fields | Category |
|---------|-------------|--------|----------|
| **Direct tenant** | DocType has its own tenant Link field | `tenant` (Link), `tenant_name` (Data, RO, FF) | tenant: (b) or (a), tenant_name: (a) |
| **Inherited tenant** | Tenant auto-populated from a parent Link via fetch_from | `tenant` (RO, FF:parent.tenant), `tenant_name` (RO, FF) | Both (a) |
| **No tenant** | Geography/reference DocTypes shared across all tenants | None | N/A |

### 8.2 Tenant Authorization Rules

1. **tenant field must NEVER be editable by end-users.** It should be:
   - `read_only: 1` + `fetch_from` for DocTypes inheriting tenant from a parent
   - `permlevel: 1` for DocTypes where admin explicitly assigns tenant
   - Set automatically in `before_insert` for DocTypes where tenant is derived from context

2. **tenant_name is ALWAYS category (a)** -- `read_only: 1` + `fetch_from: "tenant.tenant_name"`.

3. **Data isolation:** Frappe's permission system with `if_owner: 1` provides per-user isolation. Multi-tenant isolation requires additional Python filtering:

```python
def get_list_filters(user=None):
    """Add tenant filter for non-admin users."""
    if "System Manager" not in frappe.get_roles(user):
        tenant = get_user_tenant(user)
        return {"tenant": tenant}
    return {}
```

### 8.3 Compliance DocTypes with Company Field

Some compliance DocTypes (Consent Channel, Consent Method, Consent Record) have both `tenant` and `company` fields. The `company` field provides sub-tenant isolation within a single tenant:

| Field | Category | Protection |
|-------|----------|-----------|
| tenant | (b) | Admin assigns, or inherited via fetch_from |
| company | (b) | Admin assigns within tenant scope |
| tenant_name | (a) | read_only + fetch_from |
